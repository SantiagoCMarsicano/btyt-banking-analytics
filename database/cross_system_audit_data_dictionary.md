**Version:** 1.0.0\
**Script:** `scripts/audit_cross_system.py`\
**Project:** BTYT Banking Analytics --- Part I: Business Intelligence &
Performance Management\
**Status:** Pre-freeze final integrity audit

------------------------------------------------------------------------

## 1. Purpose

The BTYT Final Cross-System Audit is the final read-only validation
layer executed before freezing the synthetic banking universe and moving
to the database, SQL, and Power BI stages.

Its purpose is not to generate, recalibrate, repair, or modify data. Its
purpose is to verify that the independently generated BTYT subsystems
form one coherent analytical universe.

The audit validates relationships across:

-   customers;
-   accounts;
-   cards;
-   loans;
-   loan monthly snapshots;
-   transactions;
-   account balances;
-   branches;
-   branch performance;
-   banks;
-   bank market and financial data;
-   external shocks;
-   campaigns.

The governing principle is:

> **Python generates facts. SQL relates facts. Power BI interprets
> facts.**

The final audit verifies that the facts generated by Python can safely
be related and analyzed downstream.

------------------------------------------------------------------------

## 2. Audit philosophy

BTYT is a synthetic banking data-generating process rather than a
collection of independently randomized tables.

The audit therefore focuses on four forms of coherence:

1.  **Entity integrity** --- identifiers are unique and valid.
2.  **Referential integrity** --- relationships between datasets resolve
    correctly.
3.  **Temporal integrity** --- events and lifecycle states occur in a
    valid chronological order.
4.  **Accounting and behavioral integrity** --- observable facts
    reconcile with the underlying banking mechanics.

The audit is intentionally **read-only**.

It must never:

-   change a generated dataset;
-   overwrite a frozen output;
-   alter probabilities;
-   modify stochastic calibration;
-   manufacture missing records;
-   relax a validation rule merely to obtain `PASS`.

A failed check is evidence to investigate, not something to suppress.

## 3. Observation window

The canonical analytical observation window is:

``` text
2021-01-01 → 2026-12-31
```

Transactions and other observed events expected to belong to the
analytical universe must respect this boundary unless a specific
upstream dataset explicitly represents pre-observation lifecycle
history.

## 6. Core banking validation

### Customers

The audit verifies:

-   `customer_id` uniqueness;
-   valid registration-year values when available;
-   populated customer status when available.

Expected relationship:

``` text
customer_id
    ↓
accounts
cards
loans
campaign relationships
external customer states
```

Customers form the principal entity spine of the BTYT universe.

### Accounts

The audit verifies:

-   `account_id` uniqueness;
-   account → customer foreign key;
-   account → branch foreign key;
-   valid opening year;
-   closing year not earlier than opening year;
-   closed accounts contain a closing year.

Conceptually:

``` text
customer
   ↓
account
   ├── transactions
   ├── balances
   └── linked cards
```

### Cards

When `cards.csv` exists, the audit verifies:

-   `card_id` uniqueness;
-   card → customer foreign key;
-   linked card → account foreign key;
-   customer ownership coherence between the card and linked account.

A card linked to an account owned by another customer is considered a
hard integrity failure.

------------------------------------------------------------------------

## 7. Credit lifecycle validation

The credit audit covers:

``` text
loans.csv
loan_monthly_snapshot.csv
```

It verifies:

-   `loan_id` uniqueness;
-   loan → customer foreign key;
-   loan → branch foreign key;
-   snapshot → loan foreign key;
-   uniqueness of the loan-month grain;
-   non-negative outstanding balances;
-   non-negative actual payments.

Expected snapshot grain:

``` text
loan_id × year_month
```

The monthly snapshot represents loan state through time and must remain
compatible with the parent contractual loan.

------------------------------------------------------------------------

## 8. Transaction validation

Transactions are treated as event facts.

The transaction generator follows the ground-truth principle:

``` text
transaction intent
      ↓
chronological execution
      ↓
operational / liquidity outcome
      ↓
completed banking movement
      ↓
derived monthly balance
```

The audit verifies:

-   `transaction_id` uniqueness;
-   transaction → account foreign key;
-   parseable transaction datetimes;
-   transaction dates inside the observation window;
-   non-negative transaction amounts;
-   recognized transaction statuses;
-   failure-reason semantics;
-   transaction type/direction coherence;
-   transaction → branch foreign key when a branch is recorded;
-   valid counterparty-bank references;
-   internal BTYT transfer semantics.

### Direction contract

Credit transaction types:

``` text
TRANSFER_IN
CASH_DEPOSIT
LOAN_DISBURSEMENT
INTEREST_CREDIT
```

Debit transaction types:

``` text
TRANSFER_OUT
CASH_WITHDRAWAL
DEBIT_PURCHASE
SERVICE_PAYMENT
CREDIT_CARD_PAYMENT
LOAN_PAYMENT
```

A transaction whose direction contradicts its transaction type is a hard
failure.

### Status contract

Expected statuses:

``` text
COMPLETED
FAILED
```

Completed transactions should not contain a failure reason.

Failed transactions must contain a failure reason.

### Internal transfer semantics

When:

``` text
counterparty_type = BTYT_CUSTOMER
```

the expected semantics are:

``` text
transfer_scope = INTERNAL
counterparty_bank_id = B000
```

where `B000` represents BTYT itself in transfer-counterparty semantics.

------------------------------------------------------------------------

## 9. Account balance validation

The monthly account balance fact is expected to follow:

``` text
account_id × year_month
```

The audit verifies uniqueness of this grain.

For every account-month:

\[ ClosingBalance = OpeningBalance + Inflows - Outflows \]

Within monetary rounding tolerance:

``` text
abs(
    opening_balance
    + total_inflows
    - total_outflows
    - closing_balance
) <= 0.02
```

The audit also checks:

-   balance → account foreign key;
-   non-negative closing balances;
-   month-to-month continuity;
-   completed transaction inflows reconcile with monthly inflows;
-   completed transaction outflows reconcile with monthly outflows.

For consecutive observed months:

\[ OpeningBalance_t `\approx `{=tex}ClosingBalance\_{t-1} \]

The balance layer is therefore audited against the transaction ledger
rather than treated as an independent synthetic table.

## 10. Branch validation

The audit verifies:

-   `branch_id` uniqueness;
-   account and loan branch references;
-   transaction branch references;
-   branch-performance references;
-   uniqueness of branch-month performance when present.

Expected analytical grain:

``` text
branch_id × year_month
```

Branch performance is a derived/materialized analytical fact and should
remain reconcilable with the underlying banking universe.

## 11. Bank validation

The bank subsystem includes:

``` text
banks.csv
bank_market_weights.csv
bank_financials.csv
bank_macro_environment.csv
bank_monthly_performance.csv
```

The audit verifies:

-   `bank_id` uniqueness;
-   market-weight → bank references;
-   financial → bank references;
-   annual market-weight reconciliation;
-   macro coverage for 2021--2026;
-   bank-month performance uniqueness when available;
-   valid transaction counterparty-bank references.

Market weights may be represented as shares summing approximately to
`1.0` or percentages summing approximately to `100.0`.

The auditor accepts either representation but does not silently
normalize malformed values.

## 12. External shock validation

External shocks remain a probabilistic contextual layer.

The audit may inspect:

``` text
data/master/external_shocks.csv
data/interim/external_customer_monthly_state.csv
data/interim/external_idiosyncratic_events.csv
```

Checks include, when the corresponding columns exist:

-   shock/event identifier uniqueness;
-   shock start date ≤ end date;
-   uniqueness of customer-month shock state;
-   uniqueness of idiosyncratic event identifiers.

### Causal interpretation

The audit does **not** infer causality between shocks and previously
generated banking outcomes.

Where shocks did not directly enter an upstream generator's DGP, they
must be interpreted downstream as contextual or explanatory states
rather than proven causes of transaction, balance, or credit outcomes.

This distinction must be preserved in SQL and Power BI.

------------------------------------------------------------------------

## 13. Campaign validation

Campaign behavioral data is separated into:

``` text
campaigns.csv
campaign_customers.csv
campaign_exposures.csv
```

The core campaign sequence is:

``` text
eligibility
    ↓
selection
    ↓
delivery attempt
    ↓
successful exposure
    ↓
response
```

The audit does not manufacture campaign conversion.

### Campaign master

The audit verifies:

-   `campaign_id` uniqueness;
-   campaign start date ≤ campaign end date.

### Campaign-customer fact

Expected grain:

``` text
campaign_id × customer_id
```

Checks include:

-   unique campaign-customer relationship;
-   campaign foreign key;
-   customer membership in the frozen customer universe;
-   exposure date not earlier than selection date;
-   response date not earlier than exposure date.

### Campaign exposure fact

Expected grain:

``` text
exposure_id
```

Checks include:

-   exposure identifier uniqueness;
-   exposure → campaign foreign key;
-   every exposure belongs to an existing campaign-customer
    relationship.

### Analytical interpretation

The following distinction must remain intact:

``` text
selection ≠ exposure ≠ response ≠ conversion
```

Downstream SQL or Power BI may define observed post-campaign outcomes,
such as product adoption within 30, 60, 90, or 180 days.

Those metrics represent temporal association or analytical attribution
unless a causal design explicitly supports a stronger claim.

------------------------------------------------------------------------

## 14. Cross-system causal contract

The final BTYT universe contains several independently generated but
related stochastic subsystems.

The governing modeling principle remains:

> **BTYT models causes as probabilistic shifts in behavior, not
> deterministic assignments of outcomes. Shared causal conditions may
> influence multiple processes, but downstream realizations use
> independent stochastic streams.**

The cross-system audit checks coherence of realized outputs.

It does not replace this stochastic modeling contract and must not
introduce deterministic relationships that did not exist in the DGP.

------------------------------------------------------------------------

## 15. PASS, FAIL, and SKIP semantics

### PASS

A check was executed and its integrity condition was satisfied.

### FAIL

A check was executed and the integrity condition was violated.

A failure requires investigation.

It must not be automatically corrected or ignored.

### SKIP

The check could not be executed because an optional dataset or
compatible field was unavailable.

A `SKIP` is informational and does not by itself imply corrupted data.

However, skipped checks should be reviewed before the universe is
declared permanently frozen.

## 17. Freeze rule

The Part I universe should be frozen only after:

1.  the final audit executes successfully;
2.  every `FAIL` has been investigated;
3.  unexpected `SKIP` results have been resolved or explicitly
    documented;
4.  any remaining limitations are recorded;
5.  no generator requires a structural correction.

After freeze, regeneration should occur only for:

-   a confirmed integrity defect;
-   an intentional new version of the synthetic universe;
-   a documented architectural change.

Performance optimization alone is not sufficient reason to silently
alter a frozen world.

## 18. Downstream handoff

After final validation, the project transitions from synthetic data
generation to analytical engineering.

Expected sequence:

``` text
Final cross-system audit
        ↓
Freeze BTYT Part I universe
        ↓
Database
        ↓
SQL
        ↓
Semantic model
        ↓
Power BI
```

The generated universe becomes the analytical source of truth.

SQL should relate and transform the facts without rewriting their
historical meaning.

Power BI should interpret the facts through KPIs, cohorts, trends,
comparisons, and analytical definitions.

## 20. Reproducibility and provenance

The audit itself contains no stochastic draws.

Given identical input files, it should return identical validation
results.

For the final frozen release, provenance may additionally be
strengthened through:

-   schema manifests;
-   row-count manifests;
-   file hashes/checksums;
-   generator version records;
-   world-seed records;
-   audit output snapshots.

These additions can be implemented after the first successful
cross-system audit without changing the underlying synthetic universe.

------------------------------------------------------------------------

## 21. Final principle

The final audit exists to answer one question:

> **Do all of the independently generated pieces of BTYT now behave like
> parts of the same bank?**

Only after that answer is satisfactorily `PASS` should the project leave
the generation stage.

**Fiction, yes. Fantasy, no.**
